How It's Built is the inventory: the six projects, the services, the diagram. This page is the method — how an actuarial question turns into a table somebody else can trust, and which decisions along the way were engineering decisions in disguise.

It is written to be useful twice: as evidence of how I work, and as a reference for anyone building something similar on Google Cloud with insurance data. Every claim below points at a file in the repository.

Four Disciplines, One Table

A claims table is where four jobs meet. In most insurers those jobs sit in different teams, and the handoffs between them are where the time and the disagreements go. Building all four sides is the point of this platform.

How a Question Becomes a Table

This is the actual path taken by the Loss Triangle page, step by step. It is the shape every other page in this dashboard follows.

  1. 1
    Start from the actuarial question, not the data

    “How much of the 2021 accident year is still unpaid?” That is a reserving question, and answering it needs cumulative paid amounts arranged by accident year against development year. Nothing about the source files suggests that shape; it comes from the question.

  2. 2
    Decide the grain — this is the decision that matters

    A claim is not paid once. It pays out repeatedly over years, which is the entire reason triangles exist. So the base fact is fct_claim_payments, one row per payment, and development_year is derived at that grain from accident date to payment date. Choosing claim grain here would not produce a slow query. It would produce a wrong reserve, quietly.

  3. 3
    Pin the source contract before transforming

    stg_claim_payments declares payment_id unique and four columns non-null. A single duplicated payment does not fail anything downstream — it inflates one cell of the triangle and every development factor derived from it. The assertion is cheaper than the investigation.

  4. 4
    Transform in layers, one job each

    int_claim_payments_cumulative accumulates with a window function partitioned by accident year and ordered by development year. rpt_loss_triangle only pivots that into columns. Splitting them means the accumulation logic exists once, and the pivot can change without anyone re-deriving the maths.

  5. 5
    Assert the thing that would be invisible if wrong

    assert_payment_dates requires that no payment precedes its accident date. A negative development year is not a curiosity: it shifts money into a cell that should not exist, and the triangle still renders perfectly. The assertions worth writing are the ones whose failure looks like a valid answer.

  6. 6
    Serve a table, not a query

    The dashboard reads rpt_loss_triangle with a SELECT * and computes chain-ladder factors in the page. No business logic lives in the presentation layer, so the number on screen and the number in a notebook come from the same place.

The Layering Rule

Sixteen tables that Dataform builds, across five layers. The rule is that each layer is allowed to do one kind of work, so when a page needs a new column the question is which layer does this belong to rather than which query do I edit.

raw_ · 5 declarations

Declared, never created. Dataform reads these tables and is not allowed to write them, which keeps loading the data a separate and auditable step from transforming it. It is also the single most common way to break a first rebuild — run the workflow against an empty raw layer and it fails at the first staging model.

stg_ · 5 tables

Rename, cast, trim. Strictly one-to-one with the source, no joins and no business logic, so a change in the source has exactly one place to land. This is where the uniqueness and non-null contracts are declared.

int_ · 3 tables

Joins and derivations that more than one mart needs: enriched claims, cumulative payments, policy exposure. Not exposed to any consumer, which is what makes them safe to restructure.

dim_ / fct_ · 6 tables

The model itself, and the only layer anyone should join against. fct_claims is partitioned by accident_date and clustered on coverage_type, claim_status — the two cuts every actuarial question starts from.

rpt_ · 2 tables

Shaped for one question and cheap to read, because a dashboard page that runs a six-join query is a dashboard page that eventually times out in front of somebody.

Actuarial Decisions That Are Really Modelling Decisions

These four look like schema details in a code review. Each of them is an actuarial judgement that became permanent the moment it was written into a table.

Partition on accident date, not report date

Both dates are in the table; only one is the partition key. Every reserving and pricing cut is by accident year, so partitioning there makes the common query prune to a fraction of the table for free. Report date is the operational view — useful for claims handling, wrong as the physical layout of an analytical fact.

Derive development year once

It is computed at payment grain in the warehouse and never recomputed downstream. The alternative — every analyst deriving it in their own query — is exactly how two people produce two reserves from one database and spend a week finding out why.

Keep indemnity and expense apart

fct_claims carries total_indemnity and total_expense as separate sums. Allocated expense is not loss. Rolling them into one column overstates severity, distorts the development pattern, and cannot be undone later without going back to payment grain.

Exposure is an offset, not a feature

The frequency model is a Poisson GLM with a log link and exposure entering as an offset, so a policy in force three months is not compared directly against one in force twelve. Passing exposure as an ordinary covariate lets the model estimate a coefficient for something the arithmetic already fixes at one.

What Governance Means Here

Governance in a portfolio project usually means a paragraph promising it. These are the parts that actually run, and what each one is defending against.

  • Assertions are contracts, not tests — they execute inside the same Dataform workflow that builds the tables, so a violated assumption stops its dependents instead of being discovered in a report. Three dedicated assertion models plus uniqueness and non-null declarations on staging and marts.
  • One service account, six named roles — bigquery.dataEditor, bigquery.jobUser, storage.objectAdmin, pubsub.editor, run.invoker, and iam.serviceAccountTokenCreator, which Dataform needs in order to execute a workflow as that account. No Owner, no Editor, nothing granted because it was faster.
  • No service account keys exist — CI authenticates through Workload Identity Federation, bound to this specific GitHub repository. There is no credential file to leak, rotate, or accidentally commit.
  • Cost is bounded structurally — max_bytes_billed caps any Dataform query at 10 GiB, so a bad join fails instead of billing. Partitioning and clustering do the rest, and the dashboard caches query results for five minutes rather than re-scanning per visitor.
  • Environments separate by prefix, from one variable — dev_claims_* against claims_*, resolved in each model's config. Promotion is a variable change, not a second copy of the SQL.
  • Deploys are canaries — each revision ships with no traffic and a tag, gets smoke-tested on its own URL for content rather than a 200, and only then takes traffic. A failed check leaves the previous revision serving, so there is nothing to roll back.
  • The health check closes its own issue — a daily job asserts the site is up, BigQuery is connected, and the old URLs still redirect. Failure opens a GitHub issue; the next green run closes it. An open issue therefore means broken now, not broken once.

GCP Choices, and the Case for the Other One

A decision is only worth recording with the conditions that would reverse it. These are the four that shaped the platform.

Dataform over dbt

Native to BigQuery, so there is no runner to host, no warehouse credentials to manage, and the dependency graph and assertions come with the product at no cost.

The other one wins when: the warehouse is not BigQuery, or the team already has dbt packages, macros and a mature test library that would have to be rewritten.

Cloud Run + Cloud Scheduler over Cloud Composer

One scheduled pipeline does not need Airflow. Composer bills a floor of roughly $300 a month for an idle environment; a container that scales to zero costs approximately nothing and fails just as loudly.

The other one wins when: there are many interdependent DAGs, real backfills, per-task retries and a dependency graph a human needs to look at. That is the point where writing your own orchestrator starts costing more than renting one.

Pub/Sub + Cloud Run subscriber alongside Dataflow + Apache Beam

Both exist here on purpose. Per-message validation and insertion is stateless, so a subscriber that scales to zero is the right tool. Anything that aggregates across a stream is not, which is why P05 is a genuine Beam streaming job.

The other one wins when: the answer depends on event time rather than arrival time — windowing, watermarks, late-arriving claims, early results that get corrected. A subscriber cannot express that without rebuilding Beam badly.

statsmodels GLM over BigQuery ML

Pure premium is modelled as a Tweedie GLM with variance power 1.5, which handles a target that is zero for most policies and continuous for the rest. The fitted coefficients matter as much as the predictions, because a rate has to be explainable to a regulator, not just accurate.

The other one wins when: the training set is too large to pull out of BigQuery, or the model family on offer is genuinely adequate and keeping everything in SQL is worth more than control over the fit.

What This Deliberately Does Not Do

  • The data is synthetic. Volumes and distributions are realistic enough to exercise the patterns, and no real policyholder data was used. Treat the numbers on these pages as a demonstration of method, not as a book of business.
  • No slowly changing dimensions. dim_policy overwrites on change, so a policy that switches coverage loses its history. Correct for the questions this platform answers today; wrong the moment anyone asks a retrospective one, and a Type 2 rebuild is the honest fix rather than a patch.
  • Terraform is not applied by CI. terraform fmt -check is the only automated gate; plans and applies are run by hand. Plan-on-pull-request is the intended next step and is not wired yet, which means drift between the configuration and the live project is still caught by a person rather than a pipeline.
  • One region, no disaster recovery. Everything runs in us-central1. That is a deliberate cost decision for a portfolio, and it would be an unacceptable one for a production insurer.
  • Reserving stops at the triangle. Chain-ladder development factors are computed and shown. Bornhuetter-Ferguson, a tail factor, and any stochastic reserve with a confidence interval around it are not implemented.

Full decision records, cost estimates and post-mortems live in each project's README in the repository.

Cuatro Disciplinas, Una Tabla

Una tabla de siniestros es donde se encuentran cuatro oficios. En la mayoría de las aseguradoras esos oficios viven en equipos distintos, y los traspasos entre ellos son donde se va el tiempo y donde nacen los desacuerdos. Construir los cuatro lados es justamente el punto de esta plataforma.

Cómo una Pregunta se Vuelve una Tabla

Este es el camino que siguió de verdad la página del Triángulo de Pérdidas, paso a paso. Es la misma forma que sigue cada una de las demás páginas de este dashboard.

  1. 1
    Empezar por la pregunta actuarial, no por los datos

    «¿Cuánto del año de ocurrencia 2021 sigue sin pagarse?» Esa es una pregunta de reservas, y responderla exige montos pagados acumulados ordenados por año de ocurrencia contra año de desarrollo. Nada en los archivos fuente sugiere esa forma; la forma viene de la pregunta.

  2. 2
    Definir el grano, que es la decisión que de verdad importa

    Un siniestro no se paga una sola vez. Se paga varias veces a lo largo de los años, que es precisamente la razón de existir de los triángulos. Por eso el hecho base es fct_claim_payments, un renglón por pago, y development_year se deriva en ese grano, de la fecha de ocurrencia a la fecha de pago. Elegir grano de siniestro aquí no produciría una consulta lenta: produciría una reserva equivocada, en silencio.

  3. 3
    Fijar el contrato con la fuente antes de transformar

    stg_claim_payments declara payment_id único y cuatro columnas obligatorias. Un solo pago duplicado no rompe nada aguas abajo: infla una celda del triángulo y con ella todos los factores de desarrollo que salen de ahí. La validación cuesta menos que la investigación.

  4. 4
    Transformar por capas, una tarea cada una

    int_claim_payments_cumulative acumula con una función de ventana particionada por año de ocurrencia y ordenada por año de desarrollo. rpt_loss_triangle solo lo pivotea a columnas. Separarlos significa que la lógica de acumulación existe una vez, y que el pivote puede cambiar sin que nadie vuelva a derivar las matemáticas.

  5. 5
    Validar aquello que sería invisible si estuviera mal

    assert_payment_dates exige que ningún pago sea anterior a su fecha de ocurrencia. Un año de desarrollo negativo no es una curiosidad: mueve dinero a una celda que no debería existir, y el triángulo se sigue viendo perfecto. Las validaciones que vale la pena escribir son aquellas cuya falla parece una respuesta válida.

  6. 6
    Servir una tabla, no una consulta

    El dashboard lee rpt_loss_triangle con un SELECT * y calcula los factores chain-ladder en la página. Ninguna lógica de negocio vive en la capa de presentación, así que el número en pantalla y el número en un notebook salen del mismo lugar.

La Regla de las Capas

Dieciséis tablas que Dataform construye, repartidas en cinco capas. La regla es que cada capa puede hacer un solo tipo de trabajo, de modo que cuando una página necesita una columna nueva la pregunta sea a qué capa pertenece esto y no qué consulta edito.

raw_ · 5 declaraciones

Se declaran, nunca se crean. Dataform lee estas tablas y no tiene permiso de escribirlas, lo que mantiene la carga de datos como un paso separado y auditable respecto de la transformación. También es la forma más común de romper una reconstrucción desde cero: si se corre el workflow contra una capa cruda vacía, falla en el primer modelo de staging.

stg_ · 5 tablas

Renombrar, castear, limpiar. Estrictamente uno a uno con la fuente, sin joins y sin lógica de negocio, para que un cambio en el origen tenga exactamente un lugar donde aterrizar. Aquí se declaran los contratos de unicidad y de campos obligatorios.

int_ · 3 tablas

Joins y derivaciones que más de un mart necesita: siniestros enriquecidos, pagos acumulados, exposición de pólizas. No se exponen a ningún consumidor, y eso es justo lo que las hace seguras de reestructurar.

dim_ / fct_ · 6 tablas

El modelo en sí, y la única capa contra la que alguien debería hacer joins. fct_claims está particionada por accident_date y agrupada por coverage_type, claim_status: los dos cortes con los que empieza cualquier pregunta actuarial.

rpt_ · 2 tablas

Con la forma exacta de una pregunta y baratas de leer, porque una página que corre una consulta de seis joins es una página que tarde o temprano se cae enfrente de alguien.

Decisiones Actuariales que en Realidad son de Modelado

Las cuatro parecen detalles de esquema en una revisión de código. Cada una es un juicio actuarial que quedó permanente en el momento en que se escribió dentro de una tabla.

Particionar por fecha de ocurrencia, no de reporte

Ambas fechas están en la tabla; solo una es la llave de partición. Todo corte de reservas y de tarifa es por año de ocurrencia, así que particionar ahí hace que la consulta habitual lea una fracción de la tabla sin costo extra. La fecha de reporte es la vista operativa: útil para gestión de siniestros, equivocada como distribución física de un hecho analítico.

Derivar el año de desarrollo una sola vez

Se calcula en el grano de pago dentro del almacén y nunca se vuelve a calcular aguas abajo. La alternativa, que cada analista lo derive en su propia consulta, es exactamente la forma en que dos personas producen dos reservas distintas de una misma base y se llevan una semana averiguando por qué.

Mantener indemnización y gasto separados

fct_claims lleva total_indemnity y total_expense como sumas distintas. El gasto asignado no es siniestro. Juntarlos en una sola columna sobreestima la severidad, distorsiona el patrón de desarrollo, y ya no se puede deshacer sin regresar al grano de pago.

La exposición es un offset, no una variable

El modelo de frecuencia es un GLM Poisson con liga logarítmica y la exposición entrando como offset, para que una póliza vigente tres meses no se compare directo contra una vigente doce. Pasar la exposición como covariable normal deja que el modelo estime un coeficiente para algo que la aritmética ya fija en uno.

Qué Significa Gobierno de Datos Aquí

En un proyecto de portafolio, gobierno de datos suele significar un párrafo prometiéndolo. Estas son las piezas que realmente corren, y contra qué protege cada una.

  • Las validaciones son contratos, no pruebas — se ejecutan dentro del mismo workflow de Dataform que construye las tablas, así que un supuesto roto detiene a sus dependientes en lugar de descubrirse en un reporte. Tres modelos de validación dedicados más las declaraciones de unicidad y campos obligatorios en staging y marts.
  • Una cuenta de servicio, seis roles con nombre — bigquery.dataEditor, bigquery.jobUser, storage.objectAdmin, pubsub.editor, run.invoker y iam.serviceAccountTokenCreator, que Dataform necesita para ejecutar un workflow como esa cuenta. Nada de Owner, nada de Editor, nada otorgado porque era más rápido.
  • No existe ninguna llave de cuenta de servicio — CI se autentica con Workload Identity Federation, amarrado a este repositorio de GitHub en específico. No hay archivo de credenciales que se pueda filtrar, rotar ni subir por accidente.
  • El costo está acotado por diseño — max_bytes_billed limita cualquier consulta de Dataform a 10 GiB, de modo que un join mal escrito falla en vez de facturar. La partición y el clustering hacen el resto, y el dashboard cachea resultados cinco minutos en lugar de re-escanear por cada visitante.
  • Los ambientes se separan por prefijo, desde una variable — dev_claims_* contra claims_*, resuelto en la configuración de cada modelo. Promover es cambiar una variable, no mantener una segunda copia del SQL.
  • Los despliegues son canarios — cada revisión sale sin tráfico y con etiqueta, se prueba en su propia URL verificando contenido y no solo un 200, y apenas entonces recibe tráfico. Si la prueba falla, la revisión anterior sigue sirviendo, así que no hay nada que revertir.
  • El health check cierra su propio issue — un job diario verifica que el sitio responda, que BigQuery esté conectado y que las URLs viejas sigan redirigiendo. Si falla abre un issue en GitHub; la siguiente corrida en verde lo cierra. Un issue abierto significa entonces roto ahora, no roto alguna vez.

Decisiones de GCP, y el Argumento a Favor de la Otra Opción

Una decisión solo vale la pena documentarla junto con las condiciones que la revertirían. Estas son las cuatro que le dieron forma a la plataforma.

Dataform en vez de dbt

Nativo de BigQuery: no hay runner que hospedar, no hay credenciales de almacén que administrar, y el grafo de dependencias y las validaciones vienen incluidos sin costo.

La otra opción gana cuando: el almacén no es BigQuery, o el equipo ya tiene paquetes, macros y una librería madura de pruebas en dbt que habría que reescribir.

Cloud Run + Cloud Scheduler en vez de Cloud Composer

Un solo pipeline programado no necesita Airflow. Composer cobra un piso de unos 300 dólares al mes por un ambiente ocioso; un contenedor que escala a cero cuesta prácticamente nada y falla igual de fuerte.

La otra opción gana cuando: hay muchos DAGs interdependientes, backfills de verdad, reintentos por tarea y un grafo de dependencias que un humano necesita mirar. Ese es el punto donde escribir tu propio orquestador empieza a costar más que rentar uno.

Pub/Sub + suscriptor en Cloud Run junto con Dataflow + Apache Beam

Los dos existen aquí a propósito. Validar e insertar mensaje por mensaje no guarda estado, así que un suscriptor que escala a cero es la herramienta correcta. Cualquier cosa que agregue a lo largo del flujo no lo es, y por eso P05 es un job de streaming real en Beam.

La otra opción gana cuando: la respuesta depende del tiempo del evento y no del de llegada: ventanas, watermarks, siniestros que llegan tarde, resultados anticipados que después se corrigen. Un suscriptor no puede expresar eso sin reconstruir Beam a medias.

GLM con statsmodels en vez de BigQuery ML

La prima pura se modela con un GLM Tweedie de potencia de varianza 1.5, que maneja un objetivo que vale cero para la mayoría de las pólizas y es continuo para el resto. Los coeficientes ajustados importan tanto como las predicciones, porque una tarifa tiene que poder explicarse ante un regulador, no solo ser precisa.

La otra opción gana cuando: el conjunto de entrenamiento es demasiado grande para sacarlo de BigQuery, o la familia de modelos disponible alcanza de sobra y quedarse en SQL vale más que el control sobre el ajuste.

Lo Que Deliberadamente No Hace

  • Los datos son sintéticos. Los volúmenes y las distribuciones son lo bastante realistas para ejercitar los patrones, y no se usó información de ningún asegurado real. Los números de estas páginas son una demostración de método, no una cartera.
  • No hay dimensiones de cambio lento. dim_policy sobrescribe al cambiar, así que una póliza que cambia de cobertura pierde su historia. Es correcto para las preguntas que esta plataforma responde hoy y deja de serlo en cuanto alguien haga una pregunta retrospectiva; la solución honesta es reconstruirla como Tipo 2, no parcharla.
  • Terraform no lo aplica CI. terraform fmt -check es la única compuerta automática; los planes y los applies se corren a mano. El plan en cada pull request es el siguiente paso previsto y todavía no está conectado, lo que significa que la deriva entre la configuración y el proyecto vivo la detecta una persona y no un pipeline.
  • Una sola región, sin plan de recuperación. Todo corre en us-central1. Es una decisión deliberada de costo para un portafolio, y sería inaceptable para una aseguradora en producción.
  • Las reservas se detienen en el triángulo. Se calculan y se muestran los factores de desarrollo chain-ladder. Bornhuetter-Ferguson, un factor de cola, y cualquier reserva estocástica con un intervalo de confianza alrededor no están implementados.

Los registros de decisión completos, las estimaciones de costo y los post-mortems viven en el README de cada proyecto dentro del repositorio.
